# Contributing to FormSkills

Thank you for helping. FormSkills aims to put every Form app's released skills in one
place, to read, download, edit as your own copy and install into your agent, and it
gets there through real use and real contributions.

## Where to start

- **Use it and report what goes wrong.** A clear bug report, with steps, the version
  and your platform, is one of the most useful things you can give.
- **Look at the open issues.** Comment on one before starting larger work, so nobody
  builds the same thing twice.
- **A problem in an app's own skill** belongs in that app's repository: FormSkills
  shows the skills each app releases and never edits an original.

## Setting up

Clone the repository and run `./formskills_oc_install`, then `./formskills` (or
`formskills_oc_install.bat` and `formskills.bat` on Windows). The first installs what
the window needs; the second opens it. `./formskills dev` reads Form app checkouts
beside this one instead of released skills. The README's Quick start has the details
and the requirements.

The code lives in:

| Folder | What is there |
| --- | --- |
| `core` | `formskills-core`, the engine (Rust): the app list, the signed catalogue, fetching, the index, search, the format check, your copies, installing into agents |
| `cli` | `formskills-cli`, the command line (Rust) |
| `src-tauri` | the desktop shell (Rust, Tauri) |
| `frontend` | the window (TypeScript, Vite) |
| `setup` | `apps.py`, which generates `core/data/apps.json` from formcompiler's registry |
| `.docs/wiki` | the wiki's source |

## Before you open a pull request

Run the same checks CI runs:

```sh
(cd frontend && npm ci && npm audit && npm run typecheck && npm run build)
cargo check --locked -p formskills-core -p formskills-cli
cargo test --locked -p formskills-core -p formskills-cli
python3 -m py_compile setup/apps.py
```

CI also checks the shell scripts with `bash -n` and refuses an em dash in tracked
Markdown or an emoji in any tracked text.

- Keep each pull request to one change, with tests for what it adds or fixes.
- Write commit subjects the way the history does, in Conventional Commits:
  `feat(core): ...`, `fix(frontend): ...`, `docs(...)` (see
  [.docs/BRANCHING.md](.docs/BRANCHING.md)). Leave the version alone; the maintainer
  bumps it when releasing.
- `core/data/apps.json` is generated by `./formskills apps --compiler PATH`; never
  edit it by hand, and never copy an app's skills into this repository.
- Never loosen the catalogue's signature, digest or unpacking checks, or the path
  check when reading a skill's files. Skills are shown as text and never run: no
  `innerHTML` with skill content.
- Every colour, space and radius comes from `tokens.css`, and every `z-index` from
  `frontend/src/styles/layers.css`.
- Every new dependency, binary, font or data file gets a row in `NOTICE.md` before it
  is used.

## How changes land

Only the maintainer pushes to `main`. Everyone else forks the repository and opens a pull request into `main`. A pull request merges when all four checks pass on an up-to-date branch and the maintainer has approved it after its last push.

## Releases

A release is a version, and only the maintainer makes one: after the version is bumped on
`main`, the maintainer cuts a `compile_vX.Y.Z` branch, and formcompiler
(`nodemode-dev/formcompiler`) builds every platform and publishes them together. No
push from a contributor starts a release. See [.docs/BRANCHING.md](.docs/BRANCHING.md).
